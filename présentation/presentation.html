00 — Cadrage

Une gestion manuelle, quatre problèmes récurrents

La médiathèque veut moderniser le suivi de son catalogue et de ses emprunts. Le cahier des charges identifie quatre points de friction.

01 Suivi des emprunts

Impossible de savoir rapidement quels livres sont sortis, et par qui.

02 Livres perdus

Aucune alerte sur les retours en retard ou les ouvrages non rendus.

03 Disponibilité

Aucune visibilité en temps réel sur les ouvrages disponibles au catalogue.

04 Traçabilité

Les emprunteurs ne sont pas reliés de façon fiable à leurs emprunts.

➜ Réponse retenue : une API REST Spring Boot exposant le catalogue et le système d'emprunt, consommable ensuite par une application web ou mobile (hors périmètre de ce mini-projet).

On part toujours du besoin métier, pas de la techno. Ces quatre problèmes viennent tels quels du cahier des charges fourni par le professeur.

Insister sur le fait que le projet est backend-only : pas de front prévu, c'est une API consommée par un client externe.

00 — Cadrage

Objectifs fonctionnels et contraintes techniques

Objectifs

  • Gérer le catalogue de livres
  • Gérer les comptes utilisateurs
  • Gérer les emprunts et retours
  • Garantir la cohérence des données métier

Contraintes du CDC

  • Java + Spring Boot, architecture en couches
  • API REST, réponses JSON, erreurs cohérentes
  • Base de données relationnelle
  • Gestion des exceptions métier, code maintenable

Livrables attendus : code source complet · documentation technique · démonstration fonctionnelle · dépôt Git structuré — un projet d'ingénierie logicielle complet, pas seulement du code.

Le CDC est explicite : ce n'est pas juste "coder des CRUD", c'est analyse + conception + développement + qualité + documentation. C'est exactement la structure de notre présentation.

00 — Cadrage

Deux acteurs, deux niveaux de droits

Utilisateur

Personne enregistrée dans le système, pouvant consulter le catalogue et gérer ses propres emprunts.

  • Consulter le catalogue de livres
  • Emprunter un livre disponible
  • Retourner un livre emprunté
  • Emprunter plusieurs livres à la fois

Administrateur

Responsable de la gestion du catalogue et de la supervision des comptes et des emprunts.

  • Ajouter / modifier / supprimer un livre
  • Gérer les comptes utilisateurs
  • Consulter tous les emprunts en cours
  • Seul rôle autorisé à écrire sur le catalogue

Deux rôles seulement — c'est volontairement simple, mais ça structure toute la sécurité JWT qu'on verra plus tard : seul ADMIN peut écrire sur les livres.

Étape 02 — Analyse

Trois entités métier, six règles de gestion

Fonctionnalités par entité

EntitéAttributsActions

Utilisateurnom, email, rôleCRUD + filtrage
Empruntutilisateur, livre, dates, statutcréer, retourner, lister

Règles de gestion (RG)

  • RG-01 — un livre indisponible ne peut être emprunté
  • RG-02 — un livre, un seul emprunteur à la fois
  • RG-03 — un utilisateur peut cumuler des emprunts
  • RG-04 — un retour libère le livre automatiquement
  • RG-05 — pas d'emprunt sur une entité inexistante
  • RG-06 — un livre avec emprunt en cours reste protégé

Ces règles ne sont pas des détails : ce sont elles qui deviennent, plus tard, nos exceptions métier et nos tests unitaires. Bien les montrer ici crée le fil rouge jusqu'à la diapositive tests.

Étape 05 — Architecture

Une architecture en couches, strictement séparées

Le point à souligner : JwtFilter s'exécute AVANT le Controller, dans la chaîne de filtres servlet. C'est la frontière de sécurité — d'où le contour doré sur ce schéma.

Étape 05 — Architecture

Authentification JWT, sans état

Deux endpoints publics seulement : register et login. Tout le reste passe par JwtFilter. Le choix stateless facilite la scalabilité horizontale — pas de session à partager entre instances.
